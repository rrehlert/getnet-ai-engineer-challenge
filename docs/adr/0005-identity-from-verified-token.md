# Identity only from a verified token; dev login as the IdP stand-in

The Merchant's identity comes only from a verified JWT (`sub`, `role`, `exp`), never from the request body. In this demo, tokens are issued by `POST /dev/login`, a "log in as" endpoint enabled only with `DEMO_LOGIN=true`; it proves nothing about who the caller is and stands in for a real identity provider. The part built for real is the verification boundary: a valid token becomes the principal, an invalid or expired one is rejected (never downgraded to anonymous), and everything after it (graph state, `SupportContext`, account tools, Conversation ownership) was already designed to take identity from context, so swapping in a real IdP changes only the entry point. Requests without a token are allowed but limited to the Knowledge Agent: account questions get a "log in" reply and the Customer Support Agent never runs.
